# Conversational coach P1 implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task by task. Checkboxes record actual results. The owner requested parallel Sol feature work; keep the shared model/store/tool lane serialized and give native UI its own file ownership.

**Goal:** Add dated personal goals, conversational morning weights and workouts, and truthful native progress views to the existing Mivu diary.

**Architecture:** Extend `DiarySnapshot` and its authoritative `DiaryStore` actor. Persist new values through the existing SQLite snapshot transaction and portable archive, then expose guarded coach operations through the existing engine/tool namespace. Calculate reports from saved records in pure Foundation code; SwiftUI Charts renders those reports without becoming a second source of truth.

**Tech Stack:** Swift 6, iOS 26+, Foundation, SwiftUI, system Charts, existing SQLite3, Swift Testing/XCTest and XcodeBuildMCP. No paid service, backend or new dependency.

Native chart interaction uses Apple's supported [chartXSelection](https://developer.apple.com/documentation/swiftui/view/chartxselection%28value%3A%29) and [chart view modifiers](https://developer.apple.com/documentation/swiftui/view-chart-view), with accessible text alternatives. The later platform-integration milestone uses [App Intents and Siri](https://developer.apple.com/documentation/appintents/apple-intelligence-and-siri-ai) and explicit [HealthKit authorization](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data). These primary references were checked on 2026-10-12; documentation availability does not establish a device integration or permission grant.

**Spec:** `docs/superpowers/specs/2026-10-12-conversational-coach-design.md`; owner brief: `.superpowers/sdd/2026-10-12-coach/owner-brief.md`. Read the P0 plan and current source before implementing. ## Global constraints and file ownership

- Preserve P0 profile/day/meal/weight IDs, photos, nullable nutrients, pending captures, revisions, receipts, deleted-meal lineage, v1/v2 archive imports and English-only native design. All new Codable fields decode absent legacy keys safely.
- Bind profile ownership in `DiaryStore`; fence asynchronous results with `selectionEpoch`; validate entire tool batches before writes. Persist record and receipt together, return the stored receipt on retries with regenerated call IDs, and never say a write succeeded after a failed commit.
- Dated goals are explicit user settings. Never infer a prescription, equate an absent day with zero intake, or silently add workout energy to the food budget. Exercise adjustment is an explicit dated setting and estimated burn stays separately visible.
- Keep existing `recordWeight` behavior for manual morning entry: one entry per waking day, same ID on repeat. Add revision guards and coach paths without replacing legacy weights.
- No diabetes/celiac logic, public release claim, paid provider fallback or platform integration in P1. Preserve Dynamic Type, VoiceOver chart alternatives, reduced motion/transparency and 44-point actions.
- One worker owns `DiaryModels.swift`, `DiaryStore.swift`, `DiaryDatabase.swift`, `DiaryArchive.swift`, `CoachModels.swift`, `CoachTools.swift` and `CoachEngine.swift` at a time. Analytics owns new pure files after model interfaces freeze. UI owns `TodayView.swift`, `HistoryView.swift`, `SettingsView.swift`, `CoachView.swift`, `DiaryStyle.swift` and new progress views. Integrate on one branch after P0 is stable; one native simulator/test owner at a time.

## Additive contracts to freeze before parallel work

1. `GoalRecord: Codable, Equatable, Sendable, Identifiable` in `DiaryModels.swift`: `id: UUID`, `effectiveLocalDate: String` (`yyyy-MM-dd`), `timeZoneID: String`, `revision: Int`, `targets: NutritionValues` (each nullable; kcal and grams), `goalWeightKg: Double?`, `exerciseCreditEnabled: Bool`. One record per effective date per profile; a later record is a complete new setting, with nil meaning unset. Historical dates retain their labels across profile timezone changes. Lookup is the latest record with `effectiveLocalDate <= trackingDay.localDate`; no goal before that date. `DiarySnapshot.goals: [GoalRecord] = []`; legacy decode defaults to empty. Validate finite positive configured goals and weight, unique date/ID, bounded count, valid timezone/date and increasing revision. UI and coach both call `DiaryStore.setGoals(_ goal: GoalRecord, expectedRevision: Int?, expectedProfileID: UUID) throws -> GoalRecord`; nil revision is allowed only for a new effective date. An edit keeps the ID and increments revision. Do not reuse `updateProfile` for goals.
2. Extend `WeightEntry` with `revision: Int` and `timePrecision: MealTimePrecision` using legacy-safe decoding (`revision = 1`, `.exact` for prior entries). `DiaryStore.recordWeight` still updates the existing day ID and increments its revision. Add `setWeight(dayLocalDate: String, value: Double, unit: String, measuredAt: Date?, expectedRevision: Int?, expectedProfileID: UUID) throws -> WeightEntry` and guarded deletion by ID/revision; The captured clock resolves chat dates, while both current and historical chat without an explicit measured time store `.dateOnly`. Manual weigh-ins retain their explicitly supplied capture time. Normalize `lb` to kg only for reports; keep entered unit/value intact. One morning entry per tracking date; an existing entry needs its expected revision.
3. `WorkoutSession: Codable, Equatable, Sendable, Identifiable` in `DiaryModels.swift`: `id: UUID`, `dayID: UUID`, `performedAt: Date`, `timePrecision: MealTimePrecision`, `revision: Int`, `kind: WorkoutKind` (`strength`, `cardio`, `other`), `durationMinutes: Int`, `exercises: [WorkoutExercise]`, `estimatedBurnKcal: Double?`, `burnSource: WorkoutBurnSource?` (`userEstimate`, `modelEstimate`). `WorkoutDraft: Sendable` contains only kind, duration, exercises and burn fields; the store assigns ID/day/revision. `WorkoutExercise` has `name: String`, `sets: [WorkoutSet]`; a set has `repetitions: Int` and `loadKg: Double?` (nil for bodyweight). Validate finite, nonnegative burn/load; positive bounded duration/reps; bounded collection/string sizes; burn source only when burn exists. `DiarySnapshot.workouts: [WorkoutSession] = []`, plus deleted weight/workout IDs for stale-archive protection. New SQLite `workout` rows reference `day`; existing database opens and adds the table transactionally. Archive version 3 encodes new fields and accepts v1/v2 with empty defaults. Direct create/edit/delete store calls require selected profile and expected revision for edits/deletes. Any unspecified chat workout time uses `.dateOnly`, including same-day retrospective activity. Manual entry retains its explicitly supplied time.
4. Extend `CoachReceipt` with optional `weightID` and `workoutID`; preserve the existing required `dayID`, meal/item fields and stored `resultJSON`. `CoachWrite` adds weight creation/correction, workout creation/edit, and guarded weight/workout deletion. Operation keys use persisted turn plus kind and date for creates, and turn plus kind and record ID for edits/deletes. One create of each kind per date per turn; another session on the same date uses another turn. Actual stored IDs/revisions and receipts make regenerated-call retries a no-op; deleted targets reject stale create/edit replay, while delete replay verifies the tombstone. Add strict `log_weight`, `log_workout`, `edit_workout`, `delete_workout`, `delete_weight` declarations. Weight arguments include local date, value, kg/lb unit, expected revision when correcting, and optional measured time. Workout arguments include local date, kind, duration, named exercises with repetitions/load, optional estimated burn and its source; edits/deletes require real ID and expected revision. Unknown keys, invalid dates/numbers and model-selected profile IDs are rejected. Return committed record JSON. Goals are configured through the native form in P1 and exposed in actual context/report reads; an unrestricted model `set_goals` mutation is excluded. P2 may propose target changes with visible user confirmation before saving.
5. `ProgressAnalytics` is pure Foundation over `DiarySnapshot`, with `daily(snapshot:localDate:) -> DailyProgress`, `period(snapshot:endingOn:days:) -> PeriodProgress` (`days` is 7 or 30), and `weight(snapshot:endingOn:) -> WeightProgress`. Calendar windows are inclusive local dates in the selected profile timezone, weekly windows are seven calendar days, and displayed month means the trailing 30 calendar days. `DailyProgress` carries stored food totals, selected goal, per-nutrient `remainingFromRecorded` only where both numbers are known, day completeness/pending status, recorded workout count and separate estimated burn. Its `exerciseAdjustedKcalRemaining` exists only when `exerciseCreditEnabled` is true and all recorded workouts have known burn; it never replaces food-only remaining. `PeriodProgress` carries complete/partial/untracked/missing counts, known-intake sample counts for each nutrient, averages divided only by complete known days, adherence numerator/denominator and recorded workout count; never synthesize zero for missing days. `WeightProgress` uses at most the latest measurement per local date, normalized to kg, reports a seven-calendar-day average with observed-day count, and change between seven-day windows ending 7 and 30 days apart only when each window has at least three measured dates. Plateau readiness is `insufficientData` until first and last seven-day windows of a 28-day span each have at least three dates **and** at least 14 complete, known-kcal tracking days exist in that span; afterward it may report a stable observed trend when absolute average change is at most 0.25 kg. P2 writes the coaching explanation, never a diagnosis.

## Review focus

1. v1/v2 archive or old SQLite import with no new keys must retain exact P0 records and photos; a corrupt new row must fail the read, not disappear.
2. A model retry with a new call ID, a late profile switch or a stale direct edit must not duplicate or overwrite a goal, weigh-in or workout; failed disk write changes neither value nor receipt.
3. A day with no log, partial records, unknown nutrients or pending review must never produce a complete calorie average or fabricated remaining budget.
4. Historical dates around midnight/DST and mixed `kg`/`lb` entries must not shift days or compare unlike units.
5. Exercise burn with unknown value or disabled credit must stay separate from consumption; a sparse weight series must yield an explicit insufficient-data state.

## P2 handoff and limits

P2 can retrieve bounded `get_progress`/`get_workout` facts and existing goal/weight/workout IDs to answer questions about history, suggest meals against actual remaining targets, propose realistic activity and explain a sufficiently observed stable trend. It must ask when data is sparse, avoid extreme restriction or punitive exercise, and require explicit acceptance for goal changes. This P1 plan does not add persistent preference memory, automated coaching summaries, external fitness imports, reminders, supplements or meal planning.
